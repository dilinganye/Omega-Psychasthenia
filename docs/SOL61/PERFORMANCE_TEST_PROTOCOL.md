本轮已修改源码并临时编译，通过8项回归；没有替换游戏加载JAR，没有实机测得帧率或帧时间。掉帧原因包含已确认的重复工作，但尚不能认定其为全部原因，也不能宣称掉帧已解决。用户允许后台降频，要求侦察效果相近；本轮保留原威胁检查、报告周期、上传期限、每日最大值与阶段公式，优先移除重复修补、全区同步和舰队列表重复获取。

## 测试版本安排

1. 保留相同起点存档的独立副本，分别用于原版本与编入本轮源码的测试版本；一次只加载一个版本，切换后重启游戏。当前加载JAR由用户安排构建，代理本轮不覆盖。
2. 固定MOD列表、游戏设置、窗口大小、地图缩放、所在地点、玩家航线与时间倍率。不要把不同存档状态或不同舰队密度误作优化收益。
3. 每个场景先预热30秒，再记录60秒，重复3次。航行与暂停分别测；每次从相同起点重载。初始化后的持续性能与首次加载/阶段转换峰值分开记录。
4. 优先第一阶段，然后侦察舰密集地区，最后战争阶段。普通航行与高速航行分开；有条件时增加进入/离开星系的场景。

## 性能摘要

开发模式下打开危机开发控制界面，点击“采集性能摘要（每15秒写入日志）”。正常模式不能启用；默认关闭，重新加载清空采集。日志搜索 `PTSD performance / 15 real seconds`，包含状态修补、势力同步、新闻、侦察、报告上传与人类报告的调用次数、总耗时、平均耗时和最大单次耗时。统计项目存在嵌套调用，不要把所有类别耗时直接相加为总帧时间。

摘要统计被包裹的逻辑调用，不是游戏完整帧时间，也不是精确的逐舰队扫描计数。侦察调用次数可作为扫描活动的辅助指标；精确扫描次数若需要，应在测试构建中加独立计数。首次修补通常发生于开启采集前，不出现于该段日志属正常现象；自动测试已覆盖1000次读取只修补一次。

## 新闻验收

- 旧档第一阶段等下一轮抽取，检查记录生成、新闻分类显示、订阅推送。空白delivery兼容全部系列；显式CONDITIONAL/SCRIPTED不进入随机池。
- 令首选类别全部冷却或没有合格目标，确认尝试另一类别；同一无效候选本轮不重复抽取。两类都不可用则维持两日以内重试，不制造地点或目标。无效非空类型/目标表达式/条件触发类型应出现明确行读取错误。
- 要塞、运输、报告条件不存在时等待，出现对应对象后再投放；区分阶段不符、最早投放时间、已投放、普通冷却、数据错误及无现存目标。已存在事件失去现场对象应按原失效生命周期处理。
- 关闭订阅后新闻仍生成、任务与结算继续，仅通知不推送。没有补齐过去漏发的历史，属于本次边界。

## 侦察与旧档验收

- 同地点候选视图本地0.1日、远端0.5日更新；玩家进入地点与本模组增删舰队立即失效。依据原版BaseLocation的实时只读列表保留候选引用，外部模组增删也实时可见；可见性、坐标、战果每次重新判断。
- 比较同一日多次接触的最大兵力、跨日结算、报告队列条数/期限/上传后的证据，以及侦察阶段进度。特别测试瞬间进出观测范围，不能因缓存漏掉接触；延迟不能补造样本或重复上传。
- 测试处于逃离阶段的侦察舰失联卸载、普通侦察继续活动、陷阱保持并后续接敌、要塞撤离倒计时。不得因后台普查改变这些即时行为。
- 旧存档首次读取完成原迁移，重新加载重建运行时标记和缓存；已有调查、冷却、舰队、预算和待上传报告保留。新调查直接初始化PENDING，旧档缺失结果按原迁移判断，不凭模糊失败制造证伪。
- 势力首次加载/阶段转换进行必要同步；新增资产立即归属并安装合适监听器；后续每0.5游戏日处理十分之一地点及市场，约5日完成一轮。外部资产兼容处理存在这段后台延迟。
